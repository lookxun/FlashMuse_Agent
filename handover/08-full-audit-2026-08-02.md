## 第 1 档 · 漏钱与会随数据量爆炸

### 1.1 🔴 积分能被并发白刷（在漏真钱）

| 位置 | 问题 |
|---|---|
| `src/lib/credits.ts:141-146` | `assertUserCanUseCredits` **只判 `credits <= 0`** |
| `src/lib/credits.ts:185` | `chargedCredits = Math.min(user.credits, expectedCredits)` —— 余额触底归零，超支被静默吸收 |
| `src/app/api/image/route.ts:101` vs `:208` | **检查在前、扣费在后**，中间是供应商调用。`video/route.ts`、`chat/route.ts:91` vs `:105`、`agent-plan`、`conversation-memory`、`workflow-prompt-optimization/rewrite` 同一形状 |

**后果**：余额只剩 1 分的用户，同时发 N 个 `POST /api/image`，**N 个全部通过检查、全部执行**，
我们向供应商付 N 次钱。

**另一个独立问题（同一文件）**：`credits.ts:176-197` 是「读出来 → 在 JS 里算 → 写绝对值」。
Postgres 默认 READ COMMITTED 下 `$transaction` **不能防这个**：
两个并发扣费都读到 `credits=100`，都写 `100-10=90` → **少扣一次，静默漏收**。
`textCreditRemainder` 那个 float 累加器有同样的竞态。
⭐ 对照：`grantCredits`（`:283`）用的是原子 `{ credits: { increment } }`，**写对了**，扣费这边没跟上。

**建议修法**：
1. 扣费改成原子 `{ credits: { decrement: chargedCredits } }`（小改动，先止血）。
2. 生成前"占用/预扣"额度，或加一个每用户在途任务数上限。

**好消息（已核实，不用管）**：**客户端无法影响价格** —— `usd` 来自供应商返回的 usage，
`count` 被夹到 ≤4（`image/route.ts:19-22`），`model` 会对照管理员启用列表校验（`:93`）。
计费幂等也有 DB 级保证（`@@unique([requestId, kind])`）。
（小瑕疵：`/api/chat:75` 没查 `isTextModelEnabled`，用户能调用被管理员禁用的文本模型，但计费正常。）

### 1.4 🟠 工作流保存时读全部 canvasJson（"按需加载"只做了读那一半）
